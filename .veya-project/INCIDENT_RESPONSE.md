# hemal 异常响应流程

## 0. 发现与分级

1. 监控 agent 保留原始证据：检查名、时间、版本、日志链接、指标窗口和错误摘要；脱敏后再通知。
2. 生成稳定 incident 指纹并去重，记录 owner、优先级、状态和下一次更新时间。
3. 按影响分级：
   - **P1**：生产不可用、数据完整性/安全事件、Critical 漏洞；立即通知值班 owner 和负责人。
   - **P2**：主要功能退化、High 漏洞、失败部署、覆盖率越过门槛；当日处理。
   - **P3**：非阻断质量问题、趋势回归、监控盲点；进入 backlog，周会跟进。

## 1. 止损

- 先确认是否为误报、维护窗口或重复事件，不要通过关闭监控来消除告警。
- 生产异常优先保护用户和数据：暂停发布、限制流量或启用已验证的降级措施。
- 若最近发布高度相关，按 `PROJECT_STATE.md` 登记的回滚路径回滚；若路径为空，标记 `BLOCKED` 并升级，不执行猜测性操作。
- 安全事件保留证据、限制权限和扩散；不得删除日志或重置可能相关的凭据而不留记录。

## 2. 诊断与修复

- 建立时间线：首次出现、变更、告警、缓解、恢复。
- 对照最近代码、依赖、配置和基础设施变更，使用最小范围验证。
- 变更必须走正常 review / 发布流程；紧急修复也要记录批准人、风险和回滚点。
- 依赖漏洞：确认受影响范围，升级到可信修复版本；无法立即升级时记录临时缓解和到期时间。

## 3. 恢复与关闭

- 用独立检查确认健康端点、关键业务路径、错误率和数据一致性恢复。
- 观察一个完整稳定窗口；P1/P2 不因单次成功探测立即关闭。
- 事件关闭必须包含：根因或当前最佳解释、影响范围、开始/恢复时间、处理人、变更链接和遗留风险。

## 4. 复盘与预防

- P1 在 2 个工作日内、P2 在 5 个工作日内完成无责复盘。
- 输出可执行行动项：owner、截止日期、验证方式；优先补测试、监控、回滚和文档。
- 每周检查行动项完成率，并把架构/部署事实同步到 `PROJECT_STATE.md`。

## 状态流转

`OPEN -> TRIAGED -> MITIGATING -> MONITORING -> RESOLVED -> CLOSED`

任何阶段再次触发都回到 `TRIAGED`；无法确认影响时按更高一级处理。
